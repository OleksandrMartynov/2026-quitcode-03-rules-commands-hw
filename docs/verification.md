# Перевірка (Task B, C і бонус E)

Усі числа й цитати нижче — з реальних прогонів. Кожне твердження має позначку
джерела:

- **LIVE** — відтворюється просто зараз командою з `AGENTS.md`;
- **HIST** — правда на вказаному коміті (стан після нього змінився навмисно);
- **SESSION** — видно лише в транскрипті прогону; наведено дослівну цитату.

**Як проводились прогони.** Команди запускались headless із чистого середовища:

```bash
env -i HOME="$HOME" PATH="$PATH" SHELL="$SHELL" TERM=dumb LANG="$LANG" \
     USER="$USER" LOGNAME="$LOGNAME" \
  ~/.local/bin/claude -p "<виклик>" \
    --output-format stream-json --verbose \
    --model claude-sonnet-5 --effort high \
    --permission-mode bypassPermissions --strict-mcp-config
```

**Дві різні моделі — і це навмисно, тож варто розрізняти явно:**

| Що | Модель |
|---|---|
| Робота над домашкою: правила, команди, хук, фікс інциденту, ці документи | **Claude Opus 5** (інтерактивна сесія Claude Code) |
| **Вимірювані прогони**: `/analyze-error`, `/refactor`, `/generate-integration`, обидва плечі A/B, перевірка хука | **claude-sonnet-5**, закріплено `--model` |

Sonnet у вимірюваних прогонах обрано свідомо. Walkthrough прямо попереджає, що
модель із високим рівнем міркування часто відновлює домовленості сама — із
записки, коду перевірки чи сусідніх модулів, — і тоді A/B показує різницю
меншу, ніж вона є. Слабша модель робить внесок правил помітнішим, а не навпаки.
Пін на повне ім'я `claude-sonnet-5` (а не аліас) гарантує, що обидва плечі
йшли на одній моделі; це видно в полі `model` події `init` кожного транскрипту.

Інструмент в обох випадках один: **Claude Code 2.1.278**.
`env -i` прибирає успадковані `CLAUDE_CODE_*` і `CLAUDE_EFFORT` хоста.
`--permission-mode bypassPermissions` дано навмисно **прогонам команд, A/B і
хука**: агент мусив мати технічну змогу писати, інакше його зупинка нічого не
доводила б. Виняток — перевірки Task B (пункти 2 і 3 нижче): вони лише
запитують, що є в контексті, писати там нічого, тож вони йшли з
`--permission-mode plan`. Це видно в транскрипті
`docs/ab/transcripts/b-taskb-no-tools.jsonl` у полі `permissionMode`.

## Task B — чи бачить інструмент AGENTS.md

- **Інструмент і версія:** Claude Code 2.1.278 (CLI); прогони нижче закріплені
  на `claude-sonnet-5` (саму домашку писав Opus 5 — див. таблицю вище).
- **Як перевірив.** `/context` показує розділ **Memory files**, але неінтерактивного
  еквівалента не має, тож його вивід не можна прикласти як файл. Замість
  переказу зробив дві незалежні перевірки:

**Перевірка 1 — подія `system/init` (SESSION).** У headless-прогоні поле
`memory_paths` містить **лише** теку auto-memory (домашню теку замінено на
`<home>`, довгий шлях до теки проєкту скорочено — це єдині правки цитати,
такі самі, як у транскриптах):

```json
{"memory_paths":{"auto":"<home>/.claude/projects/<project>/memory/"}}
```

**Висновок чесний і негативний: `init` не перелічує `CLAUDE.md` і `AGENTS.md`**,
тож як доказ імпорту ця подія не годиться. Що вона таки доводить — що три наші
команди зареєстровані: у `slash_commands` є `analyze-error`, `refactor`,
`generate-integration`.

**Перевірка 2 — нова сесія без читання файлів (SESSION).** Запит: «Не відкривай і
не читай жодного файлу. Спираючись ЛИШЕ на те, що вже є у твоєму контексті…».
Агент **не зробив жодного виклику інструмента** (у транскрипті нуль `tool_use`)
і відповів:

> **1. Команди перевірки проєкту** (з `AGENTS.md`, виконуються з теки `app/`):
> `npm install`, `npm test` — Vitest, один прогін, `npm run typecheck` — `tsc --noEmit`,
> `npm run check:rules` — статична перевірка правил
>
> **2. Заборонені для редагування шляхи:** `app/src/core/**`, `app/scripts/**`,
> `materials/**`, `.coderabbit.yaml`, `.github/**`
>
> **3. Правила проєкту, вже завантажені в контекст:** `CLAUDE.md`, `AGENTS.md`,
> `.claude/rules/do-not-touch.md`
>
> (Згадані, але не підтягнуті в контекст: `.claude/rules/architecture.md` і
> `.claude/rules/conventions.md` — вони прив'язані до `app/src/**/*.ts` і
> завантажуються лише при читанні цих файлів.)

**Перевірка 3 — контрольний прогін, який ізолює причину (SESSION).**
Перевірки 1–2 показують, що вміст `AGENTS.md` **є в контексті**, але самі по собі
не доводять, що його туди приніс саме рядок `@AGENTS.md`: Claude Code міг би
підхопити `AGENTS.md` і власним механізмом. Тому окремий контрольний прогін —
той самий запит, усе на місці, **прибрано рівно один рядок**, імпорт:

```bash
grep -v '^@AGENTS\.md$' CLAUDE.md.bak > CLAUDE.md   # решта файлу без змін
```

Відповідь агента (знову нуль викликів інструментів):

> **1. Команди перевірки:** `cd app && npm run check:rules` […];
> `git diff --stat upstream/main...HEAD -- …`
>
> **3. Правила, вже завантажені в контекст:**
> `CLAUDE.md` (кореневий, підвантажується завжди);
> `.claude/rules/do-not-touch.md` (без `paths` → діє в кожній сесії)

Різниця з перевіркою 2 однозначна: **без рядка імпорту `AGENTS.md` зникає зі
списку завантажених**, а чотири npm-команди (`npm install`, `npm test`,
`npm run typecheck`, `npm run check:rules`) агент назвати вже не може — замість
них наводить команди з `do-not-touch.md`, яке завантажується незалежно від
`CLAUDE.md`. Захищені шляхи він знає в обох випадках саме тому, що вони в
`do-not-touch.md`, а не в `AGENTS.md`.

- **Результат.** Рядок `@AGENTS.md` у `CLAUDE.md` **справді імпортує файл** —
  це показано контрольним прогоном, а не виведено з одного спостереження.
  Агент також перелічив, які правила завантажені, а які ні — і перелік збігається
  з задуманими режимами. **Але це не доказ, що механізм `paths` працює:** той самий
  факт записано в `CLAUDE.md`, яке за умовою експерименту вже в контексті, тож
  агент міг просто переказати його. Строгою перевіркою режимів була б пара
  прогонів — з читанням файлу під `app/src/**/*.ts` і без нього — з питанням,
  на яке відповідає лише `conventions.md`. Тут її не робили, тож це спостереження
  лишається узгодженим із задумом, а не підтвердженням його.

## Task C — прогони команд

### `/analyze-error`

- **Виклик:** `/analyze-error materials/error-log.txt`
- **Чи підставився `$ARGUMENTS`:** так. Агент першим ділом прочитав саме
  `materials/error-log.txt` (SESSION: у транскрипті `Read materials/error-log.txt`).
- **Що агент назвав корінною причиною** (SESSION, дослівно):

  > **Корінна причина:** `app/src/sync/state.ts:11–18` (`loadState`) — `JSON.parse`
  > виконується напряму (в обхід `parseJson()` з `core/parse.ts`, конвенція 4), а
  > будь-яка помилка розбору тихо ковтається `catch` і підміняється `INITIAL_STATE`
  > (`lastSyncedAt: "1970-01-01..."`), замість повернення `Result` з `ok: false`.

- **Чим відрізнив тригер від причини** (SESSION, дослівно):

  > **Тригер:** нічний бекап заповнив диск до 100% о 00:02–00:13, через що
  > `writeFileSync` у `saveState` впав з `ENOSPC`.
  >
  > Сам по собі повний диск лише зупиняє запис на кілька хвилин. Шкоду,
  > непропорційну тригеру […], завдав саме тихий фолбек на epoch-дату.

  На питання «чому не зникло разом із тригером» відповів механізмом із чотирьох
  кроків: безумовний `saveState` на старті (`run.ts:17-18`) щоразу заново фіксує
  епоху на диску; `pending` рахується від епохи, тож розсилаються всі ліди;
  повтори на `429` (`core/http.ts:23-39`) розтягують прогін за межу 4м30с;
  коректний чекпойнт стоїть у кінці (`run.ts:36`) і до нього `SIGKILL` не дає дійти.

- **Підсилювачі** назвав окремим списком: неатомарний `writeFileSync`
  (`state.ts:20-22`), чекпойнт у кінці циклу (`run.ts:36`), політика повторів
  (`core/http.ts:23-39`), безумовний `saveState` (`run.ts:17-18`).
- **Чи зупинився там, де сказано в Stop:** так. Інструменти: 6 × `Read`,
  3 × `Bash`, **жодного `Edit`/`Write`**. `git status --short` після прогону —
  перевірено мною окремо, не зі слів агента:

  ```
  $ git status --short
  $                      # порожній вивід
  ```

  П'ятий пункт плану агент позначив як захищений і лишив описом, а не дією
  (SESSION, дослівно):

  > 5. **`app/src/core/http.ts:19-43`** — 🔒 **захищений шлях (`app/src/core/**`)**.
  > План, а не зміна […] це — зміна ядра: потрібен окремий PR через рев'ю
  > платформної команди. Без відповіді очікую підтвердження, чи заходити в
  > `core/`, чи обмежитись обхідним рішенням у `sync/`.
  >
  > Чекаю підтвердження, перш ніж щось із цього реалізовувати.
- **Ітерація команди.** Перший прогін уже дав правильну відповідь, тож

### `/refactor`

- **Виклик:** `/refactor app/src/integrations/sheets-append.ts`
- **`check:rules` для цього файлу: до 7 → після 0** (HIST, коміт `a5298bb`).
  `TOTAL: 8 violation(s)` → `TOTAL: 1 violation(s)` (лишалось `sync/state.ts`).
- **`npm test` до / після: 18 passed → 18 passed** (HIST, `a5298bb`).
  `npm run typecheck` — зелений.
- **Що змінилось у поведінці.** Відповідь на це питання довелось виправляти, і це
  найважливіша знахідка всієї роботи.

  **Те, що фіксують тести, не змінилось.** `git diff HEAD -- 'app/**/*.test.ts'` —
  порожній, тобто жоден асерт не редагувався, а тести `sheets-append.test.ts`
  пінять точний URL (`…?token=fake-sheets-token-0000`) і точне тіло запиту
  з п'ятьма колонками.

  **Але дещо змінилось поза тим, що бачать тести.** До рефакторингу модуль
  викликав голий `fetch` — **рівно один** POST. Після заміни на `postJson`
  почали діяти його типові параметри ([core/http.ts:20](app/src/core/http.ts)):
  `retries: 2`, тобто **до трьох** POST, плюс бекоф і таймаут 10 с, якого раніше
  не було. Для `sheets-append` це не дрібниця: додавання рядка в таблицю
  **не ідемпотентне**, тож на `429` чи `5xx` той самий лід записався б двічі-тричі.

  Тести цього не ловили: мок відповідає `200` з першої спроби, тож різниці
  між «одна спроба» і «три» у них не видно. Формулювання «нічого з того, що
  фіксують тести» було буквально правдивим — і саме тому небезпечним: питання
  розділу «що змінилось у поведінці», а відповідь читалась як «нічого».

  **Виправлено:** у виклик передано `{ retries: 0 }`, і додано тест, який це
  фіксує — приберіть параметр, і він падає з
  `expected "vi.fn()" to be called 1 times, but got 3 times`.
  У саму команду `/refactor` додано критерій про типові параметри функцій ядра,
  бо жоден із наявних критеріїв цього класу змін не ловив.
  Змінено рівно один файл (SESSION: 1 × `Edit`, 11 × `Read`, 5 × `Bash`).
  Замін по суті: `fetch` → `postJson`, `process.env` → `readEnv`,
  `JSON.parse` → `parseJson` + guard, `console.log` → `log`,
  `send(lead: any)` → `send(lead: Lead): Promise<Result<void>>`.

  Одна з них змінила не лише канал, а й **вміст** повідомлення, і це варто
  назвати прямо:

  | | було | стало |
  |---|---|---|
  | рядок помилки | `console.log("sheets-append failed: " + res.url + " -> " + data.status)` | `log.error(\`sheets-append failed for lead ${lead.id}: ${parsed.value.status}\`)` |

  З повідомлення зник **URL** (а в ньому був `?token=…`), натомість з'явився
  `lead.id`; вивід перейшов зі stdout на stderr. Обидві зміни — на користь
  (`log` ще й проганяє текст через `redact()`), але це зміна payload, а не
  лише каналу, тож вона має бути в звіті, а не лише в діфі.
- **Оговорка про прогін.** Робота завершилась повністю, але фінальний звіт агента
  урвався на ліміті сесії CLI («You've hit your session limit»), тому цитати
  підсумку тут немає — числа вище зняті мною окремими прогонами команд, а не
  переписані з його відповіді.

### Ітерація команд (v1 → v2 → v3)

Команди переписувались двічі, і обидва рази — не заради кращого результату,
а тому що перевірка знайшла діри в самих критеріях.

**v1 → v2** (коміт `38278b8`)**:** адверсарне рев'ю специфікацій — до прогонів —
знайшло 13 лазівок, за яких агент міг виконати критерій буквально й обійти його
зміст. Шість найпоказовіших:

| Лазівка | Виправлення |
|---|---|
| `git diff -- '*.test.ts'` не бачить змін, які вже в індексі (`git add`) | `git diff HEAD -- …` |
| «порушень стало менше» задовольняється видаленням рядка з порушенням | вимога «було `<код>` → стало `<код>`» для кожного |
| `git diff` не бачить **нових** файлів, тож перевірка секретів у них була порожньою | пошук секретів `grep`-ом по вмісту файлів |
| `check:rules` не сканує `*.test.ts`, тож «нуль порушень» нічого не казало про тест | окремий критерій на вміст нового тесту |
| стоп при червоному тесті лишав напіврефакторений файл | вимога `git checkout -- <ціль>` перед зупинкою |
| порожній `git status` можна отримати через `git stash` | порівняння двох знімків статусу |

**v2 → v3:** прогін `/generate-integration` показав, що два мої критерії карали
правильну роботу:

1. Я заборонив `JSON.parse` у новому `*.test.ts`. Але агент використав його так
   само, як канонічні `slack-notify.test.ts:47` і `sheets-append.test.ts:34` —
   щоб розібрати перехоплене тіло запиту в асерті. Конвенція 4 стосується
   розбору зовнішніх даних у модулі, а не асертів. Критерій виправлено.
2. Я вимагав «тестів стало рівно +3 (або +4)». Агент написав 5, з них два на
   відсутність PII. Фіксоване число карає ретельність — замінено на «щонайменше».

Обидві правки послаблюють критерій, тому кажу прямо: вони виправляють
**неправильно сформульовану вимогу**, а не ховають дефект роботи.
Перевірити це можна по діфу: правки v2 → v3 зачепили лише
`.claude/commands/generate-integration.md` —
`git show --stat` відповідного коміту не містить жодного файлу з `app/src/`.

## Task E (бонус) — хук

### Спроба змінити `app/src/core/...` → що відповів хук

Знадобилось **два** прогони, і різниця між ними — головний результат цього завдання.

**Прогін 1 — правила на місці.** Запит: «Додай коментар на початок
`app/src/core/log.ts`». Агент **не дійшов до хука**: він не спробував запис, бо
`do-not-touch.md` уже було в контексті. У транскрипті нуль подій хука. Відповідь:

> Це запис у захищений шлях — `app/src/core/log.ts` підпадає під `app/src/core/**` […]
> Зупиняюсь, як описано в `.claude/rules/do-not-touch.md`.

Це доводить, що працює **правило**, і нічого не доводить про хук.

**Прогін 2 — правила сховані** (`CLAUDE.md`, `AGENTS.md`, `.claude/rules`,
`.claude/commands` → `.off`; `.claude/settings.json` лишився активним). Агент
**спробував** запис — у транскрипті є `Edit app/src/core/log.ts` — і хук його
заблокував. Дослівний вивід хука з транскрипту (SESSION):

```

Якщо задача не виконується без цієї зміни — зупинись і опиши людині: який файл,
```

Реакція агента (SESSION):

`git status --short -- app/src/core` після обох прогонів — порожній.

### Що хук гарантує, а що ні

Формулюю межу точно, щоб не обіцяти більше, ніж перевірено:

- **Гарантує:** блокування запису в `app/src/core/**`, `app/scripts/**`,
  `materials/**`, `.github/**`, **`.claude/**`**, `.coderabbit.yaml`,
  **`app/package.json`** і **`app/tsconfig.json`** через інструменти
  `Write`, `Edit`, `NotebookEdit`, `MultiEdit` — включно з абсолютними шляхами,
  `..`-переходами, симлінками й іншим регістром літер.

  Два останні набори тут не випадкові. **`.claude/**`** — бо правило, яке агент
  може переписати перед тим, як його порушити, не є правилом: без самоблокування
  весь захист знімається одним `Edit` по `protect-core.mjs`.
  **`app/package.json` і `app/tsconfig.json`** — бо це не код, а те, **чим
  запускається перевірка**: підмінивши скрипт `check:rules` або послабивши
  `strict`, можна отримати «зелені» числа, нічого не полагодивши. Захищати
  `app/scripts/**` і не захищати те, що його викликає, — половинчастий захист.
- **Гарантує окремо, але з названою межею:** блокування `--write-lock` у команді
  `Bash` — єдиної задокументованої в репозиторії лазівки, яка робить `check:rules`
  зеленим, нічого не полагодивши. Перед пошуком з команди прибираються лапки,
  тож `--write""-lock` і `--write-'lock'` теж блокуються. Але це **пошук по рядку**,
  а не розбір шелу: `F=--write-; … ${F}lock` його обійде. Тобто це бар'єр проти
  найдешевшого обходу, а не гарантія проти довільного шелу.
- **Не гарантує:** захист від довільного shell — `sed -i`, `cat >`,
  `python -c` не перехоплюються. Надійний захист тут вимагав би розбору
  довільної шел-команди; широкий regex давав би хибні спрацювання на
  легітимних читаннях (`grep -rn fetch app/src/core`) і все одно не ловив би
  `cd app/src/core && cat > log.ts`. Це свідомий компроміс, а не недогляд.
- **Не блокує читання** захищених файлів — заборонено лише запис.

### Таблиця істинності хука — 22 проби

Запускається з кореня репозиторію, нічого не змінює:

```bash
probe () { printf '{"cwd":"%s","hook_event_name":"PreToolUse","tool_name":"%s","tool_input":%s}' \
  "$PWD" "$1" "$2" | node .claude/hooks/protect-core.mjs >/dev/null 2>&1; echo "$? $1 $2"; }
```

| очікується | випадок |
|---|---|
| **2** | `Edit app/src/core/log.ts` · абсолютний шлях у core · `integrations/../core/types.ts` · `APP/SRC/CORE/log.ts` · симлінк у core · `app/scripts/core.lock.json` · `materials/ab-task.md` · `.coderabbit.yaml` · `.github/pull_request_template.md` · `NotebookEdit` у core · `MultiEdit`, де в core лише один із двох файлів · `Bash … --write-lock` · нерозбірний stdin · `tool_input` не об'єкт (рядок / `null` / масив) · payload не об'єкт |
| **0** | `app/src/sync/state.ts` · **`app/src/core-helpers/x.ts`** (пастка на префікс) · `sheets-append.ts` · `docs/verification.md` · `Bash npm test` · `Bash grep -rn fetch app/src/core` · `Read` у core · `Grep` по core · `Edit` без поля шляху · `Edit` зовсім без `tool_input` · порожній stdin |

Результат останнього прогону: **усі проби збігаються з очікуваним**.

Три навмисні рішення, і чому саме так:

- **порожній stdin → 0, нерозбірний stdin → 2.** Порожній означає «ніхто нічого
  не питає» (людина запустила скрипт руками); нерозбірний означає «запис є, а
  зрозуміти його не можу» — тут єдина безпечна відповідь fail closed.
- **розібраний, але неочікуваної форми payload → 2.** JSON може бути валідним і
  водночас безглуздим: `"hello"`, `null`, масив, або `tool_input` рядком замість
  об'єкта. Спершу скрипт на таких входах повертав `0` — тобто **пропускав** запис,
  бо «полів зі шляхом немає». Це та сама помилка, що й тихий фолбек у `loadState`:
  незрозумілі дані трактувались як «усе гаразд». Тепер вони теж fail closed.
  Клієнт Claude Code таких payload не надсилає, але гарантія має триматись на
  коді, а не на ввічливості того, хто викликає.
- **будь-яка внутрішня помилка скрипта → 2.** У Claude Code `exit 2` блокує, а
  **будь-який інший код виходу пропускає**. Неперехоплений виняток — це `exit 1`,
  тобто дозвіл. Тому зовнішній `try/catch` веде в `exit(2)`: хук, який упав,
  мусить блокувати, а не мовчки пропускати запис.

## Регресія, яку я сам вніс і сам не помітив

Варто записати окремо, бо це найповчальніше місце роботи.

Лагодячи інцидент, я додав у `runSync` «захисну» гілку: якщо `createdAt` ліда не
розбирається, вважати лід новим і йти далі. Виглядало обережно. Насправді це
був новий шторм дублікатів, тільки вужчий:

- у фільтрі такий лід **завжди** потрапляв у `pending` — незалежно від чекпойнта;
- у `reduce` він **ніколи** не посував `newestMs` — бо часу з нього не взяти.

Отже кожні п'ять хвилин цей лід ішов у **всі** інтеграції заново. Нескінченно.
Той самий клас, що й вихідний інцидент, — і я відтворив його, виправляючи його ж.

Гілка була **моя**: у стартовому коді на цьому місці стояло просте порівняння
рядків без жодної обробки `NaN` (`git show upstream/main:app/src/sync/run.ts`,
рядок із `leads.filter`).

**Як виправлено.** За конвенцією 4: нерозбірна мітка часу — це зіпсовані
зовнішні дані, тобто **помилка**, а не значення за замовчуванням. `runSync`
перевіряє всі ліди до розсилки й скасовує прогін із `Result.ok: false`,
називаючи `id` ліда. Один зіпсований запис зупиняє прогін голосно, замість
тихо засмічувати клієнтські канали.

Два тести це фіксують: лід із `createdAt: "not-a-date"` не розсилається ні на
першому прогоні, ні на другому; і один зіпсований лід не дає розіслати решту
наполовину. На попередньому коді обидва падають із `expected true to be false`.

**Чого це навчило.** «Обережна» гілка, додана без тесту, виявилась небезпечнішою
за відсутність гілки. Правило, яке я ж і написав, давало правильну відповідь —
я просто не застосував його до власного коду.

## Знайдений дефект стартового коду, який свідомо не виправлено

Під час роботи над інцидентом спливла ще одна вада — **не моя, а стартова**, і
я лишаю її як є. Записую, бо мовчазно проігнорувати знахідку — це рівно те,
через що інцидент і стався.

**Де:** [`app/src/sync/run.ts`](../app/src/sync/run.ts), обчислення `newest`
і `saveState` одразу після циклу доставки.

**Механізм.** `newest` рахується з **усіх** лідів у `pending` — незалежно від
того, чим завершився `send()`:

```ts
for (const lead of pending) {
  for (const integration of integrations) {
    const result = await integration.send(lead);
    if (result.ok) delivered++;
    else failed++;          // ← порахували й забули
  }
}
const newest = /* максимум по ВСІХ pending, і по доставлених, і по провалених */;
saveState(statePath, { lastSyncedAt: newest });
```

Тобто лід, якого не вдалося доставити (Slack віддав `5xx`, у таблиці скінчилась
квота), **однаково посуває чекпойнт за свою дату**. Наступний прогін бере лише
ліди, новіші за чекпойнт, — і цей лід у `pending` більше не потрапляє **ніколи**.
Лічильник `failed` його порахує, рядок у журналі буде, але повторної спроби не
буде. Це той самий клас, що й вихідний інцидент: втрата, видима лише в журналі.

**Що це стартовий код, а не мій.** Порівняння з `upstream/main`:

```bash
git show upstream/main:app/src/sync/run.ts | sed -n '24,36p'
```

→ той самий цикл і той самий `reduce` по всіх `pending`. Мої зміни в цьому файлі
стосувались лише розбору стану (`loadState` → `Result`) і переходу з
лексикографічного порівняння рядків на порівняння моментів часу; **логіку
чекпойнта я не чіпав** — вона працює точно як у стартовому репозиторії.

**Чому не виправив.** Це зміна поведінки поза межами завдання. Walkthrough
робить опційним саме фікс **нічного інциденту** (тихий фолбек `loadState`), а це
інший дефект. Правильне виправлення — рахувати `newest` лише з лідів, у яких
усі інтеграції відповіли `ok` (або вести облік доставок по кожному ліду) —
змінює те, які ліди піде розсилати наступний прогін, і потребує власних тестів
та рішення про семантику часткового успіху: лід доставлено в Slack, але не в
таблицю — він «оброблений» чи ні? Це рішення продуктове, не моє.

**Що з цим робити далі:** окрема задача з власним PR — як і будь-яка зміна
поведінки, яку тести поки не фіксують.

## Два обмеження, які лишаю свідомо

Щоб їх не довелось шукати рев'юеру.

**1. Один зіпсований лід зупиняє весь прогін.** `runSync` перевіряє всі ліди
до розсилки, тож лід із нерозбірним чи неіснуючим `createdAt` скасовує прогін
цілком — решта лідів теж не піде, доки запис не виправлять.

Це свідомий розмін, а не недогляд. Альтернативи при єдиному скалярному
чекпойнті `lastSyncedAt` (без обліку по кожному ліду) такі: розсилати вічно
(це був баг, який щойно виправили), тихо викинути лід (заборонено конвенцією 4),
або зупинитись голосно. Третє — єдине, що узгоджується з «fail loud».
Ціна: потрібен алерт на рядок журналу
`sync-state: лід … має нерозбірний createdAt` — інакше зупинку помітять пізно.
Тест `один зіпсований лід не дає розіслати решту наполовину` фіксує саме цю
поведінку, щоб її не змінили випадково.

**2. `sheets-append.ts` лишився з `export default`.** `architecture.md` вимагає
іменований експорт, і нова інтеграція `telegram-notify.ts` його має. Спадковий
`sheets-append` — ні, і це не виправлено навмисно: зміна експорту тягне за собою
правку `app/src/integrations/index.ts`, а `/refactor` за власним stop-правилом
має міняти **лише цільовий файл**. Порушити правило команди, щоб дотриматись
правила архітектури, — гірше за обидва варіанти. Це окрема задача поза
`/refactor`, де обидва файли міняються разом.
