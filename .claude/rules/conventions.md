# Конвенції коду lead-sync

## Контекст

Воркер ходить у чужі системи й обробляє персональні дані клієнтських лідів.
Кожна конвенція нижче закриває конкретний спосіб зробити збій непомітним —
загублений таймаут, токен у журналі, пошкоджений стан, email у Slack.
`npm run check:rules` перевіряє шість із них статично.

## Правило

1. **Помилки — це значення, не винятки.**
   Функція, що може не вдатися, повертає `Result<T>` з `core/types.ts`.
   `send()` інтеграції **завжди** повертає `Result<void>` і ніколи не кидає назовні.
   Не пиши `throw new Error(...)` в `integrations/` і `sync/` — поверни
   `{ ok: false, error: "<що саме не вдалося>" }`.
   Не пиши `try/catch`, який ковтає помилку й повертає `{ ok: true }`.

2. **Вихідний HTTP — лише через `postJson()` з `core/http.ts`.**
   Не викликай `fetch` напряму: у `postJson` є таймаут (10 с), повтори на 5xx і 429
   та маскування URL у журналі — у голого `fetch` немає нічого з цього.
   Не додавай `axios`, `got`, `ky`, `node-fetch` — потрібної поведінки домагайся
   через `PostOptions` (`headers`, `timeoutMs`, `retries`, `backoffMs`).

3. **Змінні середовища — лише через `readEnv()` з `core/config.ts`.**
   Не читай `process.env` поза `core/config.ts`.
   Список потрібних змінних оголошуй у полі `requiredEnv` інтеграції — **іменами,
   не значеннями**. Значення секретів не пиши в журнал і не вшивай у код,
   навіть тимчасово й навіть у тест: у тестах — `vi.stubEnv`.

4. **Зовнішнім даним не довіряємо.**
   Будь-який JSON ззовні — відповідь API, тіло вебхука, **файл стану на диску** —
   розбирай лише через `parseJson(text, guard, label?)` з guard на очікувану форму
   (`isRecord`, `isString`, `isNumber` з `core/parse.ts`).
   Не викликай `JSON.parse` напряму.
   **Тихий фолбек заборонено:** не пиши `catch { return DEFAULT }` і не підставляй
   «значення за замовчуванням» замість помилки. Невалідний JSON чи неочікувана
   форма — це `Result` з `ok: false`, який видно в журналі. Саме тихий фолбек
   на початковий стан спричинив нічний інцидент 10.09 (`materials/error-log.txt`).

5. **Журнал — лише через `log` з `core/log.ts`.**
   Не використовуй `console.log` / `console.error` / `console.warn` поза
   `core/log.ts`: `log` проганяє повідомлення через `redact()` і маскує токени,
   а `console.*` друкує їх як є.

6. **Без `any`.**
   Не пиши `: any`, `as any`, `<any>`. Для невідомих даних — `unknown` плюс guard,
   який звужує тип. Форму зовнішньої відповіді описуй інтерфейсом і guard-функцією.

7. **Без нових залежностей.**
   У застосунку нуль runtime-залежностей — так і лишається.
   Не запускай `npm install <пакет>` і не додавай пакет у жодну з мап:
   `dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies`.
   Наявні dev-залежності — рівно три: `vitest`, `typescript`, `@types/node`.
   Код сторонньої бібліотеки не копіюй у модуль — це та сама залежність,
   лише без запису в `package.json`.
   Потрібна бібліотека — спершу опиши в PR, навіщо, і чекай відповіді.

   > `check:rules` бачить лише `dependencies` (`app/scripts/check-rules.mjs`),
   > тож `devDependencies` перевіряй очима: `git diff -- app/package.json`.
   Виняток стосується **лише** тестів: `import { … } from "vitest"` у файлах
   `*.test.ts` — це наявна dev-залежність і єдиний спосіб писати тести.
   У production-файлах (`*.ts` без `.test.`) імпорти лише відносні або `node:*`.

8. **Мінімізація даних у сповіщеннях.**
   У повідомлення в Slack, Telegram і будь-який месенджер **не потрапляють email
   і телефон ліда** — лише `name`, `source` і `budgetUsd`.
   Не пиши `lead.email` чи `lead.phone` у текст сповіщення.
   Повні дані йдуть тільки в системи обліку: таблиця, CRM.

9. **Імена.**
   Файли — kebab-case. Поле `name` інтеграції збігається з іменем файлу
   (`sheets-append.ts` → `name: "sheets-append"`).

10. **Тести поруч із модулем, без реальної мережі.**
    `*.test.ts` у тій самій теці. `fetch` підміняй через
    `vi.stubGlobal("fetch", ...)`, змінні — через `vi.stubEnv`.
    Для кожної інтеграції три випадки: успішна відправка (перевір **URL і тіло
    запиту**), відсутня змінна середовища, помилка від зовнішньої системи.

## Як перевірити

`cd app && npm run check:rules` показує шість із десяти конвенцій. Читай розділ
`by rule`:

| рядок | конвенція |
|---|---|
| `http-via-core` | 2 |
| `env-via-config` | 3 |
| `json-via-parse` | 4 |
| `log-via-logger` | 5 |
| `no-any` | 6 |
| `no-new-deps` | 7 |

**Критерій — не нуль, а дельта:** у **новому** чи переписаному коді порушень нуль,
а числа в цих рядках **не зростають** проти прогону до твоєї зміни. Тому знімай
`check:rules` двічі — до і після.

Ненульові значення на чистому репозиторії — це **спадщина**: частину коду перенесли
з n8n до появи конвенцій (див. `materials/architecture-brief.md`, розділ «Спадщина»).
Такий код переписують окремою задачею й без зміни поведінки, а не мимохідь.
Щоб побачити, де саме, дивись перелік угорі виводу й розділ `by file`.

Решту перевіряй очима — статичний чекер їх не бачить:

- конвенція 1: `grep -rn "throw " app/src/integrations app/src/sync` → порожньо.
- конвенція 8: `grep -rn "lead\.email\|lead\.phone" app/src/integrations/` →
  збіг допустимий у двох випадках: модуль системи обліку (`sheets-append.ts` —
  таблиця, а не сповіщення) і тест, який **стверджує відсутність**
  (`slack-notify.test.ts`: `expect(text).not.toContain(lead.email)`).
  Збіг у тілі сповіщення — порушення.
- конвенція 10: `cd app && npm test` — зелений, і для нової інтеграції в її
  `*.test.ts` є всі три випадки.
- Перед комітом — повний набір команд із `AGENTS.md`, розділ «Команди».
