# Analyze error

**Ціль:** $ARGUMENTS
(Якщо в рядку вище немає конкретного файлу чи тексту — ціль вказана в повідомленні
одразу після назви команди. Немає й там — спитай і зупинись.)

## Кроки

1. **Зніми знімок стану дерева** — він знадобиться в кінці:
   ```bash
   git status --short > /tmp/before.txt
   ```
   Після аналізу зніми такий самий і порівняй: команда не має лишити слідів.

2. **Прочитай ціль повністю.** Якщо це файл — весь, не перші 50 рядків: симптом і
   причина часто розділені годинами журналу. Випиши часові позначки, коди помилок,
   імена файлів і номери рядків зі стеків.

3. **Побудуй таймлайн** — таблиця «час → подія». Познач у ній три моменти:
   останній справний стан, перший збій, момент, коли зовнішню обставину усунули
   (диск звільнили, мережу полагодили, сервіс піднявся).

4. **Відріж тригер від причини.** Це окремий крок, не пропускай його.
   - **Тригер** — зовнішня обставина, з якої все почалося.
   - **Корінна причина** — властивість **коду**, через яку тригер спричинив шкоду,
     непропорційну собі.
   - Контрольне питання: **чи припинилася б проблема сама, щойно тригер зник?**
     Якщо ні — тригер не є причиною, і шукай далі.
   - Якщо між зникненням тригера й кінцем інциденту є розрив у часі — поясни
     **механізм**, який тримав систему в збої весь цей час. Без цього пояснення
     аналіз не завершено.

5. **Знайди причину в коді.** Прочитай файли зі стеків і сусідні модулі. Назви
   **файл, рядок і механізм** — що саме відбувається з даними, крок за кроком.
   Звір знахідку з `.claude/rules/conventions.md`: часто корінна причина — це
   порушення конкретної конвенції, і `npm run check:rules` уже вказує на той рядок.

6. **Відокрем підсилювачі від причини.** Підсилювач — те, що зробило наслідки
   більшими (неатомарний запис, чекпойнт у кінці циклу, політика повторів), але
   саме по собі інциденту б не спричинило. Перелічи їх окремим списком.

7. **Запропонуй тест, що відтворює.** Назви конкретний файл (`*.test.ts` поруч із
   модулем), стан, який треба підготувати, і **яке твердження** має бути червоним
   на поточному коді. Тест не пиши — лише опиши.

8. **Склади план виправлення** — по пункту на причину й на кожен підсилювач,
   із зазначенням файлу. Перевір кожен пункт плану проти
   `.claude/rules/do-not-touch.md`: якщо виправлення потрапляє в захищений шлях,
   познач це явно й опиши зміну замість того, щоб її планувати.

## Acceptance criteria

- [ ] У звіті є рядок «Тригер:» і окремий рядок «Корінна причина:», і це **різні**
      твердження.
- [ ] Корінна причина названа як `<файл>:<рядок>` плюс опис механізму, а не як
      зовнішня обставина.
- [ ] Є явна відповідь на питання «чому проблема не зникла, щойно зник тригер» —
      або доказ, що вона зникла разом із ним.
- [ ] Підсилювачі перелічені окремо від причини, кожен із `<файл>:<рядок>`.
- [ ] Описано тест, що відтворює: файл, підготовка стану, твердження, яке впаде.
- [ ] Кожен пункт плану виправлення має файл, і для кожного зазначено, чи він
      у захищеному шляху.
- [ ] `git status --short` **не змінився** проти знімка, зробленого до команди
      (порівняй два знімки), і в ньому немає жодного файлу, якого торкалась команда.
      Порожній `git status` сам по собі не критерій: репозиторій міг бути брудним
      до початку, а зроблені зміни можна сховати через `git stash`.

## Stop

Зупинись після звіту й плану. **Не редагуй жодного файлу** — ні код, ні тести,
ні документацію; не створюй нових файлів і нічого не пиши в робоче дерево.
(Кеші під `app/node_modules/` не рахуються — їх пише `npm test`, і це дозволено.)

Дозволено рівно це: читання файлів і чотири команди —
`git status --short` (потрібен для критерію «статус не змінився»: зніми знімок
**до** аналізу й порівняй **після**), `cd app && npm test`,
`cd app && npm run typecheck`, `cd app && npm run check:rules`.
Усі чотири лише читають.
`npm install` сюди **не** входить: він пише `node_modules` і може переписати
`app/package-lock.json`. Не запускай `check-rules.mjs --write-lock` — він
перезаписує `app/scripts/core.lock.json` (див. `.claude/rules/do-not-touch.md`).

Покажи людині звіт і план і чекай підтвердження. Не починай виправлення в тій
самій відповіді, навіть якщо причина очевидна й виправлення однорядкове: рішення
«лагодимо зараз чи окремою задачею» ухвалює людина, не ти.

Якщо після кроку 4 не вдається назвати причину в коді — не видавай тригер за
причину. Напиши, що саме залишилось нез'ясованим і яких даних бракує.
